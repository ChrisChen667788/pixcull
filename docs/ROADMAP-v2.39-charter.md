# v2.39 charter — 主题能就地切了;入库不再重写整个库

两项都是 owner 点的顺延项。

---

## 1. 独立页面的主题**切换控件**

v2.35 让这些页面**遵守**偏好,但它们仍然没有改偏好的办法 —— 直接打开
`/library`、或从链接跳进 `/history` 的摄影师,得先回审片工作台(module 29
的工具栏 toggle 在那儿)才能切换。

**做法:注入一个固定定位的控件,而不是往每个页面的 header 里加。**
这些页面布局差异很大、其中三个**根本没有 header**;而"每页各自接线"正是
当初十一个页面里十个漏掉引导脚本的原因。所以和 tokens/引导脚本一样,收进
`_read_template` 一处注入,放在 `</body>` 前(固定定位 + 末尾插入 ⇒ 不可能
把任何页面挤位移)。

契约与 module 29 **逐条对齐**:`dark → light → system → dark` 循环、
`localStorage["pixcull_theme"]`、`system` 走 `prefers-color-scheme` 并挂
`matchMedia` 监听保持实时跟随。有测试专门钉住这两套实现的循环顺序与存储键
不许漂移 —— 它们是同一个状态机的两份独立实现。

真实浏览器复验:

```
点击循环: 跟随系统 → 深色 → 浅色 → 跟随系统   (attr / bg 同步正确)
跨页面持久: 在 /library 切换后打开 /history,偏好与主题都保持
```

### 一个产品判断:`/share` 不注入

`/share/<run>/<token>` 是摄影师**发给客户**的交付页。它**继续遵守**主题
(客户的系统偏好会生效),但**不放应用控件** —— 那是摄影师的作品呈现,
不该带 PixCull 的 chrome,而且客户端也没有"工作台偏好"可同步。已复验:
其余 6 个页面都有 `pcThemeFab`,share 页没有。有测试两头钉住。

另外控件带 `@media print { display: none }` —— 打印交付页不该印出应用按钮。

## 2. `append_run` 改为追加,不再重写整个库

### 先量(而不是照着"理论上会慢"动手)

一次典型拍摄(2000 张)入库的耗时,随库存量线性增长:

| 库中已有 | 文件大小 | v2.38 耗时 |
|---|---|---|
| 50,000 | 102 MB | 0.37s |
| 150,000 | 307 MB | 1.08s |
| 300,000 | 614 MB | **3.30s** |

原因是 `.npy` 把 shape 写在文件头里,所以加行 = `np.vstack` 整个库再整体
重写。而 v2.34 起自动入库默认开启 ⇒ **每挑完一次片就重写一遍全库**,
30 万张时是每次 614MB 的写放大。

### 改法:无头 float32 文件 + meta 记行数

`vectors.f32` 不带任何头,行数记在 `meta.json`。追加 = `open("ab")` 直接写
新行的字节,O(新增)。

**行数不在向量文件里,正是崩溃安全的来源。** 提交协议:

1. 追加向量字节 → fsync(此时对读者不可见,meta 仍是旧行数)
2. 追加 manifest 行 → fsync(同样不可见)
3. **原子替换 `meta.json`** ← 唯一的提交点

任何一步崩溃,读者看到的仍恰好是旧的行数:`load_vectors` 按 meta 的
`n_rows` 截断(且再按文件实际大小夹一次,防 meta 虚高),`search` 还会与
manifest 长度取 min。**残尾是惰性的,不是损坏的。**

### 结果

| 库中已有 | v2.38 | v2.39 |
|---|---|---|
| 50,000 | 0.37s | **0.159s** |
| 150,000 | 1.08s | **0.380s** |
| 300,000 | 3.30s | **0.697s**(4.7×) |

检索自检:用刚入库的第 7 个向量反查,top1 = `n7.jpg`,sim = 1.0000。

### 剩下的线性项是什么(不谎称 O(1))

30 万张时那 0.697s 里:

- `load_manifest` 解析 30 万行 JSON 建去重集合 —— **0.556s**
- `load_vectors`(mmap 打开)—— 0.005s
- 向量写入本身 —— 已可忽略

也就是说**主导成本已经不是向量了,是去重扫描**。要再快得再引入一个 key
索引文件,那是又一份需要保持同步的不变量;0.556s/次对一个跑完才发生一次的
操作是可接受的。**记录在此,不假装已经 O(1)。**

### 兼容与迁移

- v2.39 之前的 `vectors.npy` 库**照常可读**(`load_vectors` 回退);
- 下次 `append_run` 时一次性迁移到 `vectors.f32`,旧文件保留(降级仍可用);
- **但 `prune` 会删掉旧文件** —— 否则降级会把用户刚要求删除的行原样复活。

## 4. 过程中发现的一件事(未修,先记)

跑门禁时遇到 skip 数在 **5 / 6 / 8 之间浮动**。查明:`test_semantic_search`、
`test_clip_cache_freeride`、`test_reel_caption` 这些真模型测试会在 CLIP 加载
失败时 skip,而 HF Hub 对未认证请求限流 —— 同一轮里反复加载就可能失败。
单独跑 CLIP 是能加载的,所以是瞬时的。

**风险在于:这些测试里的真实回归会伪装成 skip。** 其中就包括 v2.34 用来钉住
`image_embeds ≡ get_image_features` 的那条 —— 它一 skip,整个免费 CLIP 缓存
的正确性就没人守了。建议后续:给 CI/本机配 `HF_TOKEN`,或把这些测试改成
"模型缓存已存在则必须跑,不许 skip"。
