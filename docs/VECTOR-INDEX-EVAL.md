# 向量索引评估 — 当前检索方式 vs ANN 索引(2026-07)

> owner 提问:当前照片查询方式与"构建向量索引"相比孰优,若向量索引更优则纳入
> 迭代方案。本文用**实测数据**回答,不空谈。

## 先澄清一个前提

PixCull **当前已经是向量检索**——不是关键词/SQL 查询:

- `pixcull/scoring/semantic_search.py`:CLIP 图像向量(512 维,L2 归一化)缓存在
  `output/embeddings.npz`,查询时 CLIP 编码文本 → `vectors @ q` 矩阵乘算余弦 →
  `argpartition` 取 top-k(已避免全排序)。
- `pixcull/scoring/near_dup.py`:分块 `v[i:i+B] @ v.T` 求两两相似度 → 并查集
  连通分量。

所以问题的真实含义是:**要不要在现有的 brute-force flat 检索之上,加一层 ANN
索引(FAISS / HNSW / IVF-PQ)**。

## 实测数据(本机,float32,D=512)

### ① 语义搜索:检索耗时 vs 向量内存

| 照片数 | 检索耗时(含 top-k) | 向量内存 |
|---:|---:|---:|
| 1,000 | 0.02 ms | 2.0 MB |
| 5,000 | 0.18 ms | 9.8 MB |
| 20,000 | 1.44 ms | 39.1 MB |
| 100,000 | 4.38 ms | 195.3 MB |
| 500,000 | 17.64 ms | 976.6 MB |

### ② 端到端延迟拆解(这是决定性的一组)

| 环节 | 耗时 |
|---|---:|
| CLIP 文本编码(暖) | **17.4 ms** |
| 向量检索 @5,000 张 | **0.18 ms** |
| 向量检索 @100,000 张 | 4.38 ms |

**在一次 5,000 张的搜索里,检索只占端到端的 ~1%,CLIP 编码占 ~99%。**
即使把检索优化到 0ms,用户感知延迟从 17.6ms 降到 17.4ms——**无法察觉**。

### ③ 近重复分组:唯一的真实瓶颈(O(N²))

| 照片数 | 分组耗时 | 复杂度 |
|---:|---:|---|
| 1,000 | 8 ms | O(N²) |
| 5,000 | 196 ms | O(N²) |
| 20,000 | 2,441 ms | O(N²) |
| 50,000 | 13,035 ms | O(N²) |

## 结论:**当前方式更优,不纳入 ANN 索引**(近重复侧留观察项)

### 为什么 brute-force 在这个场景下是对的

1. **检索不是瓶颈,编码才是。** 数据见 ②。ANN 索引优化的正是那 1%。
2. **检索作用域是"一次拍摄",不是全库。** 端点是
   `/api/v1/runs/<run_id>/semantic_search` —— 每次只在一个 run 内检索。真实
   婚礼/活动 run 是 1k–5k 张,brute-force **0.02–0.18ms**,ANN 在这个规模下
   **建索引的开销远大于查询节省**(HNSW 建图 5k 向量约需数百 ms,而它要省的
   是 0.18ms)。
3. **ANN 是有损的。** IVF/HNSW 用召回率换速度。近重复折叠的设计原则明确写着
   "precision over recall——错误折叠两张不同的照片是代价高昂的错误"
   (near_dup.py 阈值注释)。为省 0.18ms 引入召回损失,方向是反的。
4. **零新依赖是产品承诺。** 当前只用 numpy。引入 faiss/hnswlib 会给一个
   "本地优先、pip 装完即用"的工具增加编译型依赖(faiss 的 wheel 分发在
   macOS ARM 上历来脆弱),违背 v2.31 刚打通的 `pip install pixcull` 体验。
5. **内存已经可控。** 100k 张才 195MB;而单个 run 到不了这个量级。

### 什么条件下应该重新评估(触发器)

- **出现跨 run / 全库检索**("在我所有拍摄里找这张")→ 向量数量从 5k 级跳到
  100k–1M 级,且查询频次高 → 那时 ANN 才有意义。**这是唯一真正的触发器。**
- 或 CLIP 编码被大幅加速(如换 ONNX 量化文本塔到 <2ms),使检索占比反超。

### 真正值得做的性能项(替代方案)

**近重复分组的 O(N²)** 是唯一实测出的瓶颈(20k 张 2.4 秒、50k 张 13 秒)。
但注意:**这同样不该用 ANN 解**,更简单有效的是:

1. **时间窗剪枝**:近重复几乎总在时间上邻近(重拍、同机位连续帧)。按拍摄时间
   排序后只比较 ±T 窗口内的对,复杂度从 O(N²) 降到 O(N·w)。**保持精确、零召回
   损失、零新依赖**——比 ANN 更适合这个语义。
2. 或按 scene/cluster 预分桶,只在桶内做两两比较。

**建议**:仅当有用户真的在 20k+ 单 run 上使用近重复折叠时才做(当前无此证据;
5k 张 196ms 完全可接受)。列为**观察项**而非排期项。

## 迭代方案落点

- ❌ **不加 ANN 向量索引** —— 实测证明当前 brute-force 在真实作用域(单 run
  1k–5k)下更优,且 ANN 会带来有损召回 + 编译型依赖两项真实成本。
- 👁 **观察项**:近重复 O(N²)。触发条件——出现 20k+ 单 run 的真实使用;解法用
  时间窗剪枝而非 ANN。
- 👁 **重评触发器**:若产品引入跨 run 全库语义检索,重跑本评估。

## 后续修正(2026-07,owner 指定做跨 run 全库检索后实测)

上文把"跨 run 全库检索"列为 ANN 的重评触发器。**实测后这个预判需要修正**:

| 全库规模 | brute-force 查询 | 内存 |
|---:|---:|---:|
| 100,000 张 | 8.0 ms | 195 MB |
| 300,000 张 | 22.5 ms | 586 MB |
| 1,000,000 张 | 34.5 ms | 1.9 GB |

**即使百万级,brute-force 也只要 34.5ms**(CLIP 编码 17.4ms 的 2 倍),仍在可接受
范围。真正先撞的墙是**内存**(百万级 1.9GB 常驻),不是速度。

所以跨库检索首版**仍不需要 ANN**;ANN 的价值转向**压缩**(int8/PQ),触发条件改为
"库 > 30 万张"。完整方案见
[`docs/ROADMAP-v2.32-library-search-plan.md`](ROADMAP-v2.32-library-search-plan.md)。

本文数据可复现:向量检索/近重复基准见上表参数(numpy float32、D=512、本机
Apple silicon),CLIP 编码用 `pixcull.scoring.semantic_search.encode_query`。
