# v2.44 charter — 中文识别用领域词表提准;按文字剪的编辑状态模型

owner 点的两件:提升 Paraformer 中文质量、做 (c) 按文字剪的编辑状态模型。

---

## 0. 先纠正一个我自己报错的数字

上一轮我对 owner 说「Paraformer 中文 CER 约 30%」。**那是错的。**
v2.43.2 charter 里的实测是 **9.5%**(第 2 段)、10.7%(中英混合)。

而且那 9.5% 是 **21 个字里错 2 个** —— 在这种基数上做优化**测不出信号**。
所以这一版第一步不是改代码,是把测量做扎实。

## 1. 评测集

20 句真实的婚礼/摄影现场指令 × 2 个音色 = **40 条,127s**。句子刻意覆盖
本领域最容易错的几类:与常用词同音的行话(机位/曝光/备选/长焦)、婚礼流程
词(接亲/敬酒/证婚人)、数字与单位、短祈使句(上下文少,错一个字整条字幕
就废)。

**造素材时差点在垃圾上做评测。** `say -v '?'` 把 Sandy / Shelley / Eddy 等
都列为 zh_CN,实际输出是 **0.02s 的空文件** —— 列出 ≠ 已安装。60 条里
**40 条不到 1 秒**。逐个探测后只有 3 个真能发声:Tingting(大陆)、
Meijia(台湾)、Sinji(香港)。Sinji 是**粤语**音色念中文字,对普通话模型
不是公平测试,排除。最终用 Tingting + Meijia,两种口音反而更有价值。

## 2. 结果

| 开发集(20 句 × 2 音色) | 错误 | CER |
|---|---|---|
| 基线 | 11 / 514 字 | 2.14% |
| 热词 | 7 / 514 字 | **1.36%** |

错的全是预判的那类同音行话:长焦→掌交、备选→被选、仪式→一是、眼睛→眼镜。

### 这里有个陷阱,明确避开了

剩下的错里有 `仪式`、`眼睛` —— **把它们加进热词表就是拿测试集调参**,
和 RESCORER-V3 那次「编造标签」是同一类错误,调完这个评测就没意义了。

所以词表按**领域知识先验写死**(88 条,覆盖光学/灯光/流程/婚礼四类),
然后用**10 句全新的、写词表时没看过的**句子验泛化:

| 留出集(10 新句 × 2 音色) | 错误 | CER |
|---|---|---|
| 基线 | 7 / 270 字 | 2.59% |
| 内置词表 | **3 / 270 字** | **1.11%** |

**错误数 −57%**。修好的是 `欠曝`(欠报)、`同期声`(同七声/同齐声)、
`畸变`(机变) —— **这三个词在开发集的错误里一次都没出现过**,所以是真
泛化,不是背答案。

### 接法

`load_hotwords(extra)` = 内置词表 + 调用方追加。后者才是真实用户的价值所在:
场地名、新人姓名 —— 通用词表不可能知道,而摄影师的录音里全是这些。
CLI `--hotword/-H` 可重复。Whisper 的 prompt 偏置机制不同,**明确不假装
两者是同一个开关**,传了会记一条 log 而不是静默忽略。

### 词表差点装不进用户机器

打包白名单只写了 `data/*.json`,而词表是 `.txt` —— 构建出来的 wheel 里
**没有它**,功能等于没有。v2.43.4 刚建的 `test_packaging.py` 一测就现形。
已补 `data/*.txt`,并把词表钉进该测试的必检清单。

## 3. (c) 按文字剪 — 编辑状态模型

`pixcull/scoring/edit_model.py`,纯 `(start, end)` 算术,不碰模型 /
ffmpeg / 浏览器,所以能穷举测试。

**三条设计:**

**① 源永不修改。** 编辑是叠在不可变转录之上的一组删除区间,剩余文本、
剩余画面、EDL **全部推导得出**。另一种做法(改一份可变副本)需要人工保持
「保留区间」和「可见文本」同步,而每次 undo 都是它们错位的机会。

**② 记操作日志,不存快照。** undo 弹栈后重放。转录规模下这很便宜,而且
**undo 无法恢复到任何操作序列都产生不了的状态**。

**③ 精度跟着数据走,而且明说。** Paraformer 每个字都有真实时间跨度
(v2.44 起 `Segment.char_spans` 保留),所以能按词剪且落在真时间上;
Whisper 只有段级时间。**对没有字级时间的段请求词级剪切会被拒绝**,而不是
在段内线性插值 —— 那是在伪造模型从未给过的精度,会把切点放到错误的帧上。
`EditSession.precision` 告诉 UI 现在是哪种模式,好决定要不要提供选词。

混合数据一律降为 `segment`:一半能用一半误导,比不提供更糟。

## 4. CLI 端到端抓到一个纯单测看不见的 bug

`pixcull transcribe` → `pixcull cut`,第一次跑就报:

```
2 lines · 3.3s · segment-level edits available
bad --drop-chars '0:0-3': segment 0 has no per-character times
```

内存里 `precision=word`,**存盘再读回来就退化成 segment**:写入端正确
(JSON 里 `char_spans` 10 对),`load_transcript` **没把这个字段读回来**。

**所有内存单测都是绿的。** 这正是「能跑但够不着」那一类。已修(且回读为
tuple —— JSON 没有 tuple,类型漂移只在存盘后才现形),并补 4 条持久化测试。

## 6. 过程中的一次自伤,记下来

变异测试后用 `git checkout -- pixcull/scoring/transcribe.py` 还原,
**把该文件这一版所有未提交的改动一起冲掉了**(8 处)。v2.43.3 在
USER-GUIDE.md 上刚犯过同样的错。

**教训:变异测试要用备份文件还原(`cp bak`),不要用 `git checkout` ——
工作区里有未提交改动时,它还原的是 HEAD,不是变异前。**
已全部重做并真机复验行为一致。
