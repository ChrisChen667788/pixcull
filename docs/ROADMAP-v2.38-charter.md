# v2.38 charter — 给自己刚铺开的浅色主题做对比度体检

**主题:** v2.35 和 v2.37 把浅色主题铺到了十几个此前从未渲染过浅色的页面,
**但没人验过那对对比度做了什么**。这一版去量,而不是假设。

顺带记录一次**被测量否掉的优化**——这比记录成功更有用。

---

## 0. 先说被否掉的那个:XMP 边车"stat 风暴"

剖析优化后的冷启动时,`_row_has_develop_settings` 引起了我的注意:它对
**每一行**调 `read_develop_settings()`,而后者第一件事是
`image_path.with_suffix(".xmp").exists()` —— 2 万张就是 2 万次文件系统探测,
而且若边车存在还要读取+正则解析整个文件。

理论很顺:改成每个目录 `scandir` 一次、建集合、成员判断,把 2 万次 stat
变成 1 次目录列举。实现了,也确认了功能等价(4000 张带边车的 run,
`has_develop_settings` 2000/4000 完全一致)。

**然后一量,是更慢的:**

| 场景 | 基线 | "优化"后 |
|---|---|---|
| 4000 张、一半带 .xmp | **0.349s** | 0.390s |
| 8000 张、零边车 | **0.592s** | 0.610s |

两个场景都慢 3–5%,没有一个变快。原因很直白:macOS APFS 会缓存目录项,
`exists()` 本就接近免费,我在上面再加一层 frozenset 构建 + 每行查表,
纯属净开销。

**已整体回退。** 我可以辩称"在慢速网络盘上会赢",但那是没测过的猜想,而
代价是一段带失效语义的缓存要长期维护。**基于没被验证的理论保留复杂度,
是负收益。**

(过程中还闹了个乌龙:第一次验证我查的键名是 `has_develop`,实际是
`has_develop_settings`,于是看到 `0/4000` 一度以为自己改坏了功能。查清楚
之后才发现功能一直是对的。)

## 2. 真正的发现:`--muted-soft` 在给正文上色

对共享 tokens 逐对算 WCAG 对比度:

| | 浅色 | 深色 |
|---|---|---|
| `--fg` on `--bg` | 16.73 ✅ | 14.50 ✅ |
| `--fg-2` | 10.59 ✅ | 10.59 ✅ |
| `--muted` | 5.76 ✅ | 6.51 ✅ |
| `--accent` | 6.99 ✅ | 9.28 ✅ |
| **`--muted-soft`** | **3.01** ⚠️ | **3.65** ⚠️ |

调色板整体是健康的 —— 浅色铺开**没有**引入回归。唯一的问题是
`--muted-soft`:它被用在 **9.5–11px 的正文**上(时间戳、提示、输入框
placeholder、快捷键标签、相似度读数)。WCAG 的"大字"从 18.66px 粗体 /
24px 起算,所以这些文字要的是完整的 4.5:1,而它没有。

### 为什么不是"把这个 token 调深就完了"

解方程发现:要在更深的表面(`--surface-3` #dddddd)上也达到 4.5,浅色的
`--muted-soft` 必须几乎等于 `--muted` 本身 —— **"比 muted 更弱的一档"在
浅色下没有合规空间**。

所以这是个设计判断,不是取色问题:**`--muted-soft` 从此只用于装饰**
(分隔符、chevron、圆点、hover 边框、空状态 SVG 描边 —— 这些走 3:1 的
非文本门槛),**所有正文用途改用 `--muted`**。共 16 处:12 处在页面模板 /
serve_app,4 处在 CSS 模块(我第一遍 grep 漏了 `src/modules/*.css`)。

另外两处判断:

- `.lp-collapse` 是**可点击按钮**,glyph 就是它的标签 —— 交互控件给可读
  的一档,改 `--muted`;
- `.crumb-divider`(面包屑分隔符,`user-select:none`)和 `summary::before`
  的 `content:"›"` 是纯装饰,保留。

浅色 `--muted-soft` 顺手从 `#8f8f93`(3.01,贴着 3.0 的刀锋)调到
`#858589`(3.43),给非文本门槛留出余量。

## 3. 静态 token 分析 vs 真实渲染 —— 差点漏掉的一步

审片工作台的表面不是 hex,而是 v2.21 的 **OKLCH 三变量推导**
(`oklch(0.975 0 0)`)。也就是说:**我的静态测试解析 `_DESIGN_TOKENS_CSS`
的十六进制值,完全可能过,而真实页面挂**。

所以又在真实浏览器里量了一遍。第一次量出 `--fg` 对比度 = **1.00** ——
不可能的数,一看就是我的脚本坏了:正则把 `oklch(0.205 0 0)` 的三个数当成
RGB 读了。改成**把颜色画到 canvas 上读像素**(不管源色彩空间都能拿到真
sRGB)后:

```
浅色 bg=rgb(247,247,247) card=rgb(253,253,253) —— 五个层级全部达标
深色 bg=rgb(22,22,22)    card=rgb(29,29,29)    —— 五个层级全部达标
```

OKLCH 推导出的 sRGB 与十六进制 token **完全一致**,所以静态测试确实有
代表性。但这件事只有量过才知道。
