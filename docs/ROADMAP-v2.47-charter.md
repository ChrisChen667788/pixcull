# v2.47 charter — 第一次量审片页;差点报了一个不存在的 bug

功能/性能/交互三条线里,性能这条最久没量过。charter 里有库索引(v2.39)
和去重扫描(v2.40.1)的数字,**唯独没有摄影师真正盯着的那个页面**。

---

## 1. 量到的数字(合成 run,不加载模型,只测服务路径)

| 照片数 | 首次(冷) | 再次(热) | 页面大小 | 每张字节 |
|---|---|---|---|---|
| 200 | 1.88s | 0.01s | 1275 KB | 6529 |
| 800 | 0.09s | 0.04s | 2611 KB | 3342 |
| 2000 | 0.15s | 0.04s | 2529 KB | 1295 |
| 5000 | 0.36s | 0.04s | **2529 KB** | 518 |

200 张那个 1.88s 是首个请求付的模板加载,不是规模效应(后面更大的 run
反而更快)。**热请求全部 0.04s,服务路径没有性能问题。**

## 2. 但页面大小在 2000 张之后不再增长

5000 张和 2000 张**送出完全一样的字节数**。数一下:三种规模的页面里
`filename` 都恰好出现 **800 次**。

这是 v2.18 的**渐进式注水**:首屏只内联 800 行,其余后台分片拉取,而
summary / 人脸 / 地点在**全量行**上计算,所以首屏计数就是对的。**设计是
对的,不是静默截断。**

## 3. 差点报错一个 bug —— 记下来,因为过程比结论重要

顺着注水这条线查下去,发现 `/api/v1/runs/<id>/rows` 只返回 **8 个字段**,
而完整行有 **52 个**。缺的包括 `rubric_stars`(6 轴评分)、`advice`
(V20 建议信封)、全部轴分数、人脸、GPS。

我当时的判断是:**一场婚礼 2000–4000 张,第 801 张之后全都没有评分和建议。**
如果为真,这会是本项目最严重的一个缺陷。

**它不为真。** 客户端拉的是 `/results_rows/<id>`,那是另一个处理器
(`_serve_runs_rows`),返回全部 52 个字段 —— 构建产物里确认、真实响应
里确认,`rubric_stars` / `advice` / 轴分数全在。

把我带偏的是 `serve_app.py` 里的一句**过时注释**:

```
# the page pulls the rest in the background
# via /api/v1/runs/<id>/rows (same _build_results fields, ...)
```

**这句话两处都错**:页面不走那个 URL,而那个 URL 也不是全字段。

### 为什么这仍然值得修

注释不是装饰。下一个改注水逻辑的人照着它走,就会真的把页面接到 8 字段
端点上 —— 那时"第 801 张之后没有评分"就成真了。**这是一个还没发生的
bug 的种子。**

## 4. 改了什么

- 注释改成事实,并写明两个端点的差异与后果;
- `tests/test_rows_endpoints.py`(5 条)把这件事钉住:
  - **构建产物**必须仍从 `/results_rows/` 注水(查产物,不只查源码);
  - iOS 端点必须保持 8 字段投影,**不许长回全字段**(否则重新引入它当初
    要避免的载荷膨胀);
  - 两个端点必须声明**不同的 schema**;
  - **不许再出现一句注释说 api/v1 那个是全字段**。
- 把上面那张性能表写进测试的 docstring —— 数字有出处才有意义。

## 5. 两次自纠,都在测试写法上

- 用固定 4000 字符窗口截函数体,**溢到了隔壁函数**,于是测试在它没打算
  看的代码上失败。改为按 `def` 边界取。
- 断言 `"rubric_stars" not in body` 又失败:那个词出现在**docstring 里**
  (原文正是"strip the heavy advice blob, rubric_stars, …")。**注释里提到
  一个字段,不等于代码里输出它** —— 改为剥掉 docstring 后只查代码。

## 6. 验收

- 5 条测试全绿,**三次变异全部正确变红**:页面改从别处注水 / iOS 端点长回
  全字段 / 注释再次写成 api/v1 全字段。
- 版本 2.46.0 → 2.47.0 lockstep。

## 7. 结论:性能这条线本身没有待办

热请求 0.04s、注水设计正确、库索引 v2.40.1 已优化过。**没有据此提出优化,
因为量不出问题。** 本版的产出是一条被堵住的错误路径和一张有出处的基线表。
